# Development Log

How Pyosi was built during the Meta Global AI Developer Hackathon: what the product is, the decisions that shaped it and the evidence for each, and what was learned. Measurements are in `docs/eval-log.md`; the test method is in `docs/test-plan.md`; known limits are in the README. Dates are the days the work was done.

Pyosi's AI feature runs on Meta's Muse Spark model through the Meta Model API (see section 2). The code, tests and documentation were written with Claude Code (Claude Sonnet 5.5), a coding assistant used as a development tool; it is not part of the product.

## 1. What Pyosi is, and how the description changed

**Where the idea comes from.** The author's own work. As a product manager, the author always marks a screenshot of a problem before sending it; earlier, as a machinery engineer at a shipbuilding company, the author put photos in slides and added marks and comments for vendors and stakeholders, because communicating with visual content worked better. An informal check with five people (all use screenshots daily; three mark them regularly and find it needs a separate program or looks untidy; two rarely mark) is summarized in `docs/product-brief.md`. It is five people from the author's circle, not a sample, and the target user is still an assumption.

**The first idea (2026-10-27).** Upload a screenshot and rough technical notes; get numbered callouts and bounding boxes with a short explanation each. The first header sentence was "Turn screenshots and rough notes into clear visual explanations". Primary users: engineers who share screenshots in bug reports and reviews.

**The description that replaced it (2026-10-30).** The product itself stayed the same; what changed is how it is described. The first sentence says what the tool produces (annotations). The new one says what the person does with it: *Pyosi identifies the part of a screenshot you are talking about, and marks it.* Reason: people usually send a screenshot together with a message, and the value is in finding which part the message refers to, not in writing annotations. What changed: the header sentence, the README opener, the demo and the measurements (message-style notes were added as test cases). The code, the prompt and the app behaviour did not change. The primary user in the product brief became "anyone who sends a screenshot together with a message that asks for a change or a check".

## 3. Lessons learned

1. **The model locates; the code computes and validates.** Asking for item positions and computing the gaps gave repeatable numbers where asking for the numbers did not.
2. **What the model sees matters as much as what it is asked.** Enlarging small images, padding below instead of above, and padding phone screens to a square each changed accuracy more than prompt wording did.
3. **One run is a story, three to five runs are a measurement.** The same input gave different boxes on different runs; a tester's bad result did not reproduce in three requests. For users this means a result can differ between presses of Generate, which is why the boxes and texts are editable.
4. **The response format is guidance, not enforcement.** Pyosi sends the model a schema (the fields an answer must have). An empty item list still came back in about 1 of 21 distance entries after the schema said it was required. The answer was to report it visibly, not to repair it.
5. **Do not adopt a fix because it solves one problem.** The v14 format removed one error and made the last gap silently disappear in 2 of 3 runs, which is worse for a user than a visible error; overall it was not better (21 of 30 against 24 of 30).
6. **A test case can be wrong, not only the model.** A truth box that held a label plus its value, a row that also held label bars (D7), a case that expected nothing located when the note mentioned a real title (D5), and a hover case where the image itself points to one element (CM4) were each corrected in the case after the answers were seen, with the author's approval, and written down. For the text, message and plural cases the truth and the pass rules were written before the run and not changed afterwards (T4 stays a failure).
7. **The cases and the prompts have the same author (the assistant), so some cases are kept aside.** Keeping cases aside does not remove the shared authorship. It guards against a different problem: a case you watch while changing the method stops being independent evidence, because the method ends up fitted to it. The padding method was chosen on one phone screen and then checked on a second one that was not used for choosing; some other cases were not used while changing prompts (`docs/test-plan.md`).
8. **Saying "not found" is a feature.** Pyosi does not invent a mark for something that is not on the screen. In the cases built to have no matching element, the model answered "not found" in nearly every run.
9. **Fix the rule, not the screenshot.** Patching the one case you saw lets the same bug come back in another form; stating the rule it breaks (a badge must not cover what the notes talk about) fixes every case at once.

## 4. Open items

**Known limits.** The current limits are listed in the README ("How well does it work?", under Known limits). Measured on text screens: a whole table cell or chat message gets a tight box (median overlap 0.85 to 0.98); a phrase inside a sentence is placed right but loose (about 0.6); plural references ("all the delivery dates") found every item in 11 of 12 runs, and on one invoice table all three boxes sat about 14 px below the amounts. About 5% of requests time out or fail.

### To explore later (none of this is planned before the deadline; each needs a decision)
- **Show how stable a result is.** The same input can give different boxes (lesson 3). Running Generate more than once and flagging answers that disagree would tell the user when to doubt a mark. It multiplies the request count, needs a way to match entries between runs, and does not fix an offset that repeats every time.
- **Try `strict: true` in the response format.** The app sends the schema with `strict: false`. The Meta API rejects the app's schema with `strict: true` (HTTP 400: `additionalProperties` is required to be false). With that added in a test-only copy of the request, D1 and D9 passed 6 of 6 runs with no empty item list (2.6 to 5.1 s). The case where the empty list occurred (D2) was not tested, so it is not known whether `strict: true` removes that failure (lesson 4).
- **Invalid answers.** About 1 in 20 distance entries comes back without naming its two items; the app shows an error for that entry and the user can press Generate again. Two ways to reduce it: retry automatically (one more request each time), or guess the items from the entry's label (a repair, which goes against the rule that invalid output is never repaired).
- **Image shapes.** Tested: modern phone screenshots (about 2.2:1 tall, for example 390x844) and wide strips. Not tested: older 16:9 phones (1.78:1, for example 1080x1920), long scrolling captures taller than 3:1, and tablets. The phone padding was not run end to end in a real browser with the real model, and its effect on upload size and response time was not measured.
- **Improving the known weak spots** listed in the README's Known limits (thin or small targets, plural references to icons, long lists of items).
